## Phase 3 decisions (made 2026-11-04/05 by the developer during Phase 3; status ADOPTED unless noted - change freely, but keep the safety rules D-016 to D-029 intact)
| ID | Decision | Notes |
|---|---|---|
| D-030 | **Installment status stays derived, never stored.** The LLD step "update the installment status" is satisfied INSIDE the review transaction by the submission-status change, because the installment status is computed from the submissions (D-020). The review result returns the derived installment status, and tests assert it. | A stored column would create a second source of truth that could disagree with the submissions. |
| D-031 | **Review state machine.** Only `pending_review` can be decided; Verified / Needs Correction / Rejected are terminal for that submission. A conditional `UPDATE ... WHERE status='pending_review'` under row locks makes exactly one concurrent reviewer win. A student replaces a Needs Correction or Rejected submission with a NEW linked submission (D-022); the old row and its review are never edited. `payment_reviews` has a unique index on `submission_id` (one review per submission). **OPEN-10 closed**: both Needs Correction and Rejected allow a linked replacement; "permanent" applies to that submission record. | If a later phase wants "re-open a decision", drop `payment_reviews_one_per_submission` in a new migration and add the transition deliberately. |
| D-032 | **Obligation uniqueness is case-insensitive** (new unique index on `lower(period_label)` per student + academic year); period labels are trimmed and whitespace-collapsed. Bulk creation uses insert-skip: a student who already has the period is skipped (counted and reported), never duplicated or overwritten. If every target already has it, the request fails with a clear message. | Old exact-match index kept. |
| D-033 | **Record filters.** A "record" is one installment with its latest submission. "Payment month" filters the installment **due-date** month; the payment **date range** filters the latest submission's payment date (the date the student says they paid). Receipt-status filter includes "No receipt submitted". Installment status is filtered in SQL with a CASE twin of `deriveInstallmentStatus` (a test proves they agree). Page size 25; sort columns are a fixed whitelist; every value is a bound parameter; LIKE wildcards in search text are escaped. | Pending clarification from Miss Jean if "payment month" should mean the payment date instead. |
| D-034 | **Schedule edit locks.** Paid: nothing can change (no edit, no removal). Pending Verification: only the due date. Has Needs Correction/Rejected history: amount and due date, but not the academic year / period. No receipts: everything, and the installment may be removed. Rules are re-evaluated under a row lock when saving, so a stale edit page cannot bypass them. | D-035 | Dashboard definitions: Overdue count = D-018 rule (Overdue, plus past-due Requires Resubmission). **Upcoming deadlines = unpaid installments due from today up to 30 days ahead** (`UPCOMING_WINDOW_DAYS`). ## Phase 4 decisions (2026-11-05, ADOPTED by the developer unless noted; change freely but keep the safety rules D-016 to D-041)
| ID | Decision | Notes |
|---|---|---|
| D-042 | **Email queue = the `notifications` row.** `email_pending=true` + `email_status='queued'` means "worker should try". The worker (`src/lib/email/queue.ts`) CLAIMS due rows in one `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING` with a 120 s lease, counting the attempt at claim time; sends; records EVERY attempt as an `email_deliveries` row linked by `notification_id`; on success sets `email_pending=false, email_status='sent'`. A DB check constraint enforces `email_pending => email_status='queued'`. The worker touches only notifications/email_deliveries, never submissions or reviews. | Satisfies LLD 11.3 and Phase 4 Step 4 (items 1-9). |
| D-043 | **Retry policy.** Transient errors (network, timeout, HTTP 408/425/429/5xx) retry with backoff 1, 5, 30, 120 min, 5 attempts max. Other 4xx are permanent: `email_status='failed'` at once. Failed rows are never retried automatically; the administrator retries one or all on `/admin/email` (audited as `email_retry` / `email_retry_all`; only status `failed` can be retried so a sent email is never re-sent). Provider `Idempotency-Key = pnpay-notif-<id>-r<round>` (round +1 per manual retry) so a crash after the provider accepted a message cannot send a second copy. | Resend's idempotency behaviour is NOT verified against the live API. |
| D-044 | **Reminder eligibility.** Installment unpaid AND not awaiting review (a student who already submitted a receipt is not told to pay), active student with a VERIFIED email. Dedup key (installment, kind, due date) = unique index `payment_reminders_once`; reminder row + notification + queued email are created in one transaction under the installment row lock. A rescheduled installment gets a fresh reminder. | Excluding "pending" goes one step beyond the LLD's "exclude paid"; one line to change in `reminders.ts`. ## Batch change (2026-11-05, requested by the project owner)
- Registration asks for **Batch** (2026, 2027 or Alumni) instead of Year level. `users.batch` (migration 0005); `year_level` stays in the table, unused, for old rows.
- Each batch pays **24 monthly installments (2 years)** and has its own start date. Admin > Payment schedules > "Create a payment plan for a batch": the admin enters the first and last due date (max 24 months); one installment per month is created. Existing periods are skipped, so re-running also covers late registrants.
- Single-installment scopes are now: all / one batch / one student. Records filter by batch.
- Receipts can be stored in PostgreSQL (`RECEIPT_STORAGE=postgres`, migration 0004); keep `RECEIPT_MAX_BYTES` <= ~4,000,000 on Vercel (4.5 MB request limit).

## Batch plans (2026-11-06)
- The admin's "payment plan for a batch" is now SAVED (`batch_plans`, migration 0008). Students already in the batch get it when it is saved; every student who registers into the batch later gets the whole saved plan automatically, in the same transaction as their account (`assignBatchPlanToStudent`). Months already in the past are included and therefore show as Overdue for a late registrant (owner's choice).
- Saving a plan for a batch with no students yet is allowed. Saving a new plan replaces the template used for future registrations; existing installments are never changed or duplicated.
- Verified-payment deletion (migration 0007) was already in this codebase; it needs migrations 0006-0009 applied to the production database (docs/neon-run-migrations-0006-0009.sql).

## Account deletion (2026-11-06)
- A student can delete their own account (`/student/account`, password + typing DELETE). An administrator can delete any STUDENT account from the student's record (types the student ID). The administrator account cannot be deleted this way.
- Deletion removes the account, installments, submissions, stored receipt images (queued in orphaned_uploads if storage fails), notifications, sessions, tokens and email records. The append-only review log is KEPT but detached (migration 0009 makes payment_reviews.obligation_id nullable / ON DELETE SET NULL, and the trigger still permits only that detaching). Admin deletions write a `student_deleted` audit event (student ID, batch, counts); self-deletions have no admin actor and write none.
